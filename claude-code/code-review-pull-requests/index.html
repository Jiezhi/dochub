    Read and request reviews on a pull request

    Read Code Review findings on your GitHub pull request, respond to or dismiss them, and request a review with @claude review.

    Code Review is a managed service that an Owner in your Claude organization turns on for a set of GitHub repositories. Once it's on, Claude reviews pull requests in those repositories and posts its findings as inline comments, a summary in the review body, and a check run named Claude Code Review. A review never approves or blocks your pull request, and the check run never concludes as a failure.

    An Owner controls when reviews run and how thorough they are for each repository.

    If your plan doesn't include Code Review, you can still have Claude review your branch from a Claude Code session: see Review locally with /code-review.

    Severity levels

    Claude posts each finding as an inline comment on the lines concerned and marks it with one of three severity levels:

    Marker Severity Meaning
    🔴 Important A bug that should be fixed before merging
    🟡 Nit A minor issue, worth fixing but not blocking
    🟣 Pre-existing A bug that exists in the codebase but wasn't introduced by this PR

    When the review recorded its reasoning, the finding has a collapsed Why this was flagged section. Expand it to read why Claude flagged the issue and how it verified the problem.

    To change what Claude flags in your repository or how it ranks severity, see Customize Code Review.

    Respond to findings

    You can merge without responding to a finding, unless your repository's own rules require it. If its branch protection requires conversation resolution, resolve each finding's thread before you merge.

    To clear a finding, resolve its thread or push a fix.

    • Dismiss it without a code change: resolve the thread yourself on GitHub. Replying alone doesn't dismiss a finding.
    • Fix the issue: change the code and push. The next review of the pull request resolves its earlier thread when it judges the issue fixed, whether that review runs automatically on your push or you request it.
    • Explain or disagree: reply to the comment. Claude doesn't respond right away, and a reply doesn't start a review. The next review of the pull request reads the replies on its earlier findings, and can resolve the thread or post one follow-up reply. If the same kind of finding keeps coming back, ask a maintainer to add a rule to REVIEW.md.

    To get that next review without pushing, comment @claude review as a top-level pull request comment.

    Check run output

    The Details link on the Claude Code Review check run opens the findings in one table sorted by severity, including any finding whose inline comment GitHub didn't accept:

    Severity File:Line Issue
    🔴 Important src/auth/session.ts:142 Token refresh races with logout, leaving stale sessions active
    🟡 Nit src/auth/session.ts:88 parseExpiry silently returns 0 on malformed input

    A finding that has a line but wasn't posted as an inline comment appears as an annotation in the Files changed tab, on the lines concerned. Important findings show in red, nits in yellow, and pre-existing bugs in gray.

    The check run concludes as neutral, or as skipped when an automatic review didn't run because a push changed no files. It never concludes as a failure, so a finished review doesn't fail a required check. If you don't see findings, or a review didn't run, see Troubleshoot Code Review.

    Read the result from a script

    To gate a merge or post a summary from your own CI, parse the last line of the Details text with gh and jq. That line is a machine-readable comment.

    From your shell, list the commit's check runs and take the id of the Claude Code Review run. Replace OWNER and REPO with your repository owner and name, and <commit-sha> with the pull request's head commit:

    ```bash theme={null}
gh api repos/OWNER/REPO/commits/<commit-sha>/check-runs --jq '.check_runs[] | {id, name}'
```

    Read the counts from that check run, replacing CHECK_RUN_ID with the ID:

    ```bash theme={null}
gh api repos/OWNER/REPO/check-runs/CHECK_RUN_ID \
  --jq '.output.text | split("bughunter-severity: ")[1] | split(" -->")[0] | fromjson'
```

This prints a JSON object with a count per severity and its keys in alphabetical order, for example `{"nit": 1, "normal": 2, "pre_existing": 0}`. The counts include findings from earlier reviews of the pull request whose threads are still open.

    Have your script handle these cases:

    * **`normal` is above zero**: fail the job if you want to gate the merge. The `normal` key holds the count of Important findings, so Claude found at least one bug worth fixing before merge.
* **The line is missing**: treat it as no verdict rather than as zero findings. A check run for a review that failed, timed out, was canceled, or was superseded by a newer one has no such line, and some completed reviews have none either.

    Request a review

    If your pull request is a draft or comes from a fork, automatic reviews skip it, so request the review with a comment command. To get a review on your pull request, do one of these:

    • Open it or mark it ready: in a repository set to Once after PR creation or After every push, a review starts when you open or reopen the pull request, or mark a draft ready for review.
    • Comment a command: post @claude review on the pull request.
    • Push a commit: a push starts a review in a repository set to After every push, or on a pull request you subscribed with @claude review always.
    • Click Re-run: after a review fails or times out on a pull request that isn't from a fork, run it again from the check run.
    • Wait for the automatic retry: a review whose session was interrupted is retried once automatically. The check run's summary says when that's happening.

    Comment commands

    Post one of these commands as a comment on the pull request:

    Command What it does When to use it
    @claude review Starts a single review without subscribing the PR to future pushes You want one review now, such as on a pull request in a repository set to Manual, or another review right away in the other modes
    @claude review always Starts a review and subscribes the PR to push-triggered reviews going forward You want every subsequent push to start a fresh review, such as on a high-priority PR in a repository set to Manual
    @claude review once Same as @claude review: starts a single review without subscribing The same cases as @claude review

    For any of these commands to start a review, all of these conditions have to hold:

    • Post it as a new top-level pull request comment, not an inline comment on a diff line and not the body of a review. Editing an earlier comment doesn't count.
    • Put the command at the start of the comment, with always on the same line as the rest of the command. Capitalization doesn't matter.
    • You need write, maintain, or admin permission on the repository. Claude checks this with GitHub for each person who comments, and comments from bots don't start reviews.
    • The pull request must be open.

    When the command is accepted, a Claude Code Review check run appears on the pull request with the title Code review queued.... The title changes to Code review in progress... when the review starts. Claude may also react to your comment with 👀, but that reaction can appear when no review starts, so look for the check run instead.

    If a review is already running on the pull request's latest commit, a new request doesn't start a second one.

    Before a July 2026 update, @claude review subscribed the PR to push-triggered reviews. If you relied on that behavior, comment @claude review always instead.

    What a later review covers

    A later review that starts on its own, such as after a push, focuses on what changed since the last review and posts fewer nits and pre-existing findings. Its summary counts what it left out, in a line that ends "found and not posted" or "outside the scope of this re-review and not posted."

    To get a review that leaves none of these out, comment @claude review. It covers the whole pull request again.

    Review drafts and pull requests from forks

    Automatic reviews skip both of these, so request the review with a comment command:

    • Draft pull requests: a comment command runs on a draft, so you can request a review before you mark the pull request ready. Pushes to a draft don't start reviews, even after @claude review always. The subscription takes effect once you mark the pull request ready.
    • Pull requests from forks: Claude doesn't review a pull request from a fork automatically, regardless of the repository's Review runs setting. To start one, comment @claude review on the pull request. The conditions for comment commands still apply, and the write access you need is to the base repository, not the fork.

    On a pull request from a fork, @claude review always works too, but doesn't subscribe the pull request to reviews on later pushes. Clicking Re-run on the check run doesn't start a review there.

    Use Code Review alongside the Claude Code GitHub Action

    If the repository also runs the Claude Code GitHub Action in interactive mode with its default @claude trigger phrase, an @claude review comment starts the Action as well. To keep the two apart, set the Action's trigger_phrase input to a different phrase.
